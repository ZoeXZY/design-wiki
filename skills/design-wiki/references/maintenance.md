# 入库、裁决、发布和复核

先运行rules取得目标规则和sha256，再把资料转换为候选。原正文、条件、例外、来源位置应可回查。用户只是要求检查或整理时，停在候选/问题清单；不要自行决定发布。

## 候选格式

```json
{
  "rule_id": "WCAG-2.5.8",
  "base_rule_sha256": "替换为rules返回的真实sha256",
  "patch": {"min_width": 30, "min_height": 30},
  "material": {
    "title": "本地项目尺寸政策修订",
    "text": "这里应填写真实修订依据和适用范围。本示例30×30仅用于构造演示，不是官方标准。",
    "source_note": "填写文档名称、版本、条款位置，或明确写为本地构造实验"
  },
  "conflict_notes": []
}
```

不要照抄示例作为真实来源。min_width/min_height适用于2.5.8和2.5.5；1.4.3使用thresholds.normal和thresholds.large。三类规则均可修改summary。其余字段不在当前公开修订接口中。
候选正文最少20字；正文和来源要有实质内容，不为通过长度检查而填充。
可选registered_document_id连接已登记材料快照；关联材料变化后原批准失效。reported_qc为fail会阻止入库；unknown不代表内容已经核验。

执行submit后，取得candidate.id。向用户展示实际字段差异、来源和未决冲突。无明确的具体批准时不编造approve。

## 裁决格式

```json
{
  "candidate_id": "真实候选编号",
  "decision": "approve",
  "reviewer": "实际作出决定的人或明确标注的验收程序",
  "reason": "写明为什么在该项目范围接受这次修订",
  "evidence": "写明已经阅读并核查的原文与对应条件",
  "conflict_resolution": "有冲突时写明如何裁定；不得只写同意"
}
```

退回使用reject，保留原规则。不把当前模型名字写成用户名字，不把程序验收记录写成学生本人审核。
原工作流要求人工裁决；只有在隔离的测试工作区中，才用明确标注的程序裁决验证流程。
用户在现有对话已明确批准该候选的实际内容时，记录该授权与依据，继续执行，不重复索取同一批准。

## 发布和复核

1. decide后，preview --id候选编号；读取判断变化、预计结论改变和qa_items。
2. 确认与已批准内容一致，再publish --id候选编号 --preview-id刚返回的编号。
3. 预览后发生其他状态变化，旧预览可能失效；重取预览并检查差异。不要强改状态JSON绕过检查。
4. 从publication的affected_judgment_ids逐条复核，或在界面“维护复核”操作。
5. 相关旧问答在history中标为needs_review。确有重答授权时，以原问题、同范围和parent_id发起新问答；原答案不会改写。
6. 输出发布编号、实际受影响范围、复核结果与仍需补充的条件。

判断依据完整时，24×24目标在本地阈值30×30下可由pass变为fail。预置D01未说明所有例外，结果可能为unknown，这是应保留的不确定性。
范围不同、条件不充分或无关字段变化不能直接认定条款冲突。发布记录中的影响数是发布当时的历史统计，不能当成当前未完成队列长度。

本地规则发布不改变W3C官方版本。不要给本地构造数字添加“官方修订”标签，也不要把某条通过扩大成整体合规。
